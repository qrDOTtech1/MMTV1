Spec complete ENGINEBTB3 (Steven, 04/08) — projet futur, pas encore lance.

Tu es Claude Code et tu dois intégrer un moteur de trading ultra-low-latency pour Polymarket appelé ENGINEBTB3.

BTB3 = Better Than Better.

Ce moteur n'est pas seulement un copy engine.
Ce moteur doit :
- détecter les meilleurs signaux
- exécuter les trades réels le plus vite possible
- minimiser la latence
- minimiser le slippage
- minimiser les fees
- maximiser le fill quality
- maximiser le PnL net
- fonctionner sur les marchés crypto 5 min et météo court terme
- être robuste en production
- être modulaire
- être améliorable en continu

Objectif principal :
Construire une architecture de trading Polymarket qui est plus rapide, plus propre, et plus rentable que les approches classiques Python/TypeScript sur les marchés 5 min crypto et sur les marchés météo courts termes.

==================================================
PRINCIPES DE CONCEPTION
==================================================

- Hot path ultra-rapide
- Ingestion séparée de l'exécution
- Exécution séparée du scoring
- Scoring séparé du post-trade review
- Priorité absolue à la vitesse réelle
- Priorité absolue à la qualité du fill
- Priorité absolue à la robustesse du signal
- Rust sur le chemin critique si cela améliore les performances
- Python possible pour l'orchestration, l'analyse, le reporting, et les backtests
- Pas de calculs inutiles dans la boucle critique
- Pas de requêtes réseau inutiles
- Pas de polling si un WebSocket existe
- Pas de reconstruction d'objet coûteuse dans le hot path
- Pas de stratégie lente qui bloque l'exécution
- Pas de gros frameworks qui ajoutent de la latence sans bénéfice
- Pas de sur-architecture abstraite qui ralentit le bot
- Pas de copier aveuglément : toujours mesurer le post-fee edge réel

==================================================

Créer une couche d'ingestion temps réel qui utilise :
- WebSocket pour les prix externes

- REST uniquement quand nécessaire
- Connexions persistantes
- Keep-alive
- Pas de polling inutile
- Flux séparés pour :
  - CEX price feeds
  - Polymarket book / market updates
  - leaderboard / trader feeds
  - weather-related updates
  - market metadata
  - fee changes
  - position state
  - order state

Le système doit :
- recevoir les données le plus tôt possible
- normaliser les flux
- timestamp chaque événement
- stocker le snapshot local le plus à jour possible
- maintenir un local state rapide
- éviter de recalculer tout à chaque tick

À prévoir :
- thread/process séparé pour l'ingestion
- buffer interne pour les événements
- state cache local
- resync logic
- stale data detection
- feed health detection

L'exécution doit :

- signer vite
- transmettre vite
- confirmer vite
- annuler vite
- remplacer vite
- éviter les ordres obsolètes
- éviter les ordres sur des marchés déjà passés

Le moteur doit supporter :
- buy yes

- sell yes
- sell no
- cancel order
- replace order
- batch cancel si utile
- batch submit si utile
- hot path execution timing
- order priority logic
